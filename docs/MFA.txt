**용어 정리**
모놀리식
" 한 저장소에 하나의 앱과 관련된 모든 코드와 리소스를 넣는 방식 "
싱글레포
- 단독으로 동작하는 앱, 독립적이고 범용적인 라이브러리 형태의 프로젝트
모듈러 레포
" 소스 코드를 분류하여 여러개의 모듈로 나누고 모듈을 각각의 패키지로 만들어 필요한 패키지를 가져다 쓰는 방식 "
- 패키지간의 정의된 관계가 없다면 MONOREPO가 아니고, 이러한 패키지를 잘 관리하며 하나의 레포에서 관리하면 MONOREPO 이다.
멀티레포(=폴리레포)
" 모듈로 나누어 모듈마다 레포를 가지고 관리하는 방식 "
- 여러개의 페로지토리가 서로 유기적으로 관계를 가짐.
- 단점 : 히스토리를 추적하기 어렵다. 프로젝트 설정이 일관적이지 못하다. 기존 코드 활용성이 낮다.
- 장점 : 의존성이 낮다. ci/cd가 간편하다.. 저장소가 가볍다.
모노레포(=하나의 레포에서 관리하는 모듈러 레포)
" 잘 정의된 관계를 가진 여러개의 개별 프로젝트가 포함된 단일 레포지토리"
- 내부에 여러 패키지가 유기적으로 서로 관계를 가짐.
- 필요 지식 : 모듈간의 의존성 설계, 모노레포 도구 학습, 프로젝트 npm 개발 설계 학습
- 단점 : 과도한 의존성, 복잡한 ci/cd, 저장소가 무겁다.
- 장점 : 히스토리를 추적하기 쉽다. 일관된 프로젝트 설정이 가능하다. 기존 코드를 활용할 수 있다.

# 모노레포 설계

**모노레포 구현**
1. 모노레포 도구 선정 https://monorepo.tools/ (예, terborepo, nx, rust 등)
2. 통합 방법 설계
- 빌드 통합 
  - 빌드 타임에 패키지를 통합하여 배포후 운영하는 방식
  - 패키지 변경마다 앱을 재배보 해야하기 때문에 모노레포 독립적 원칙에 대해서는 맞지 않아 비추천
- 런타임 통합 기술
  - iframes 으로 통합 (과거 방식)
  - 웹 컴포넌트 통합 (웹표준, Shadow Dom, custom element, 구형 브라우저 호환)
  - 자바스크립트로 통합
  - 모듈 federation (번들링 도구에서 federation기능을 사용하는 방식: webpack, vite)
- SPA 프로젝트 통합
  - Linked SPA vs Unified SPA
  - Unified 방식은 별도의  App Shell 필요
3. 공통 모듈 설계 및 인터페이스 설정
- 공통 모듈 설셰를 위해 빌드타임의 공통 모듈이 필요하다(라우팅 모듈)
- 재사용한 컴포넌트, 공통 설정 또는 유틸리키, 인프라 레벨 등등
4. 디자인 시스템
- 하나의 프로젝트를 여러 레포로 관리하기에, 디자인 시스템 정책이 반드시 검토되어야 한다.

# 프로젝트 개발 도구
- Backend : Node.js
- 패키지 매니저: npm, yran, pnpm
- 빌드 도구: lerna, nx, rush, turborepo
- 트렌스파일, 번들링 도구

**패키지 매니저 진화**
- npm -> yarn classic > pnpm > yarn berry
- npm의 플랫 프로젝트/의존성을 관리하는 구조에대한 불편함을 개선하면서 진화 하였다.

**모노레포 빌드시스템 도구**
- 모든 패키지매니저에는 workspaces 기능이 있고, 이 기능은 작은 프로젝트에서는 큰 불편함은 없지만, 규모가 커질수록 느려짐을 느낌다.
- 역할 
  - 캐싱을 통한 작업실행속도 향상
  - 패키지 분석
  - 학습곡선 필요
